Audit · Application Themes

Theme system review: seven palettes, one contract

A source-level audit of every application theme in the EOD Charting Platform: token coverage, contrast, chart-palette parity, theme switching and persistence. Twelve findings emerged. Seven were fixed in this change set with regression tests; five remain documented with a recommended path.

Verdict

The architecture is sound; the colour contract had drifted.

Themes are implemented the right way: a single data-theme attribute on <html>, a CSS custom-property layer for application chrome and a separate, curated ChartTheme palette for the canvas renderer. All seven themes define the complete token set, light and dark variants are genuinely distinct, and the existing UX-12 contrast test already guarded normal text.

The weakness was not structure but discipline at the edges: semantic colours were used as text without a text-safe variant, persisted chart colours from a dark-only era silently overrode every theme's candle palette, one dialog shipped a hard-coded navy palette, and nothing prevented the CSS palette and the chart palette from drifting apart.

Outcome: each theme now renders its own chart palette, semantic text colours clear WCAG AA (4.5:1) on all four panel surfaces, the keyboard focus ring is an explicit token in every theme, and the first paint no longer flashes the dark default when the last session used a light theme.

How theming actually flows

Theme registry
src/features/app/themeService.ts — APP_THEME_IDS, labels, normalizeAppThemeId, applyAppTheme, and the seven CHART_THEMES palettes used by the canvas.
Chrome tokens
src/styles/global.css — :root (Midnight Slate Pro) plus one [data-theme="…"] block per theme, all consumed through CSS custom properties.
Selection UI
src/components/SettingsDialog.tsx → General → Theme. Applies live and reverts on close-without-save. The dropdown is the only theme control; an experimental palette preview strip was removed as ambiguous.
Startup
src/RootApp.tsx reads the application profile and applies the stored theme; public/theme-boot.js mirrors it before first paint.
Chart palette
src/components/ChartCanvas.tsx calls getChartTheme(currentTheme, customChartColors); custom chart colours come from the profile settings.
Guards
themeContrast.test.ts, classicLightRefined.test.ts, ChartTheme.test.ts and the new themeSystemAudit.test.ts.

Findings

High F-01 · Persisted dark-era chart colours overrode every theme's candle palette Fixed

The profile defaults candleUpColor = #26a69a / candleDownColor = #ef5350 were written as if the user had chosen them, then merged over the theme palette on every render. Selecting any light theme therefore produced the generic teal/red candle pair instead of the curated light palette: #26a69a measures 2.72:1 on Classic Light's --bg2 (below the 3:1 non-text minimum), while the theme's own #059669 measures 3.77:1. Grid and crosshair were already special-cased against their legacy defaults; candles were not.

src/features/app/themeService.ts · getChartTheme() candleUp = filteredCustom.candleUp // always #26a69a from DEFAULT_SETTINGS candleDown= filteredCustom.candleDown // always #ef5350 from DEFAULT_SETTINGS
Fix: legacy default values are now treated as “not customised” for candles, wicks and volume, exactly like the existing grid/crosshair handling. Real user picks still win.
High F-02 · Signal Triggers dialog shipped a hard-coded dark palette Fixed

SignalSettingsDialog.tsx defined its entire surface in literals (#121e2b container, #0e1726 footer, #1a293b rows and inputs, #f8fafc text). In Classic Light, Deep Light and Classic Light Refined the dialog stayed dark navy with near-white labels, breaking the theme completely.

19 hard-coded colours in one component · 0 CSS custom properties before the fix
Fix: every surface, border and label now resolves from --bg2/--bg3/--control-bg/--border/--border2/--text/--text-dim/--text-mute/--accent/--red.
High F-03 · Semantic colours were used as text without a text-safe variant Fixed

--green, --red and --accent are brand and fill colours, but 63 sites used them for text (status lines, validation hints, section titles, price changes). Several themes failed 4.5:1, worst on raised surfaces:

Medium F-04 · Launching in a light theme flashed the dark default Fixed

The theme is stored in the Tauri application profile and read asynchronously, while index.html painted a hard-coded #0b0f16 body. Every launch of a light theme therefore produced a dark flash before React applied the stored theme.

Fix: applyAppTheme mirrors the applied theme into localStorage['eod.appTheme']; a classic (non-inline, CSP-safe) public/theme-boot.js applies it before the renderer bundle runs, and the pre-CSS style block paints a theme-appropriate background.
Medium F-05 · Nothing prevented CSS tokens and chart palettes from drifting Fixed (guarded)

The same palette is expressed twice: CSS custom properties for DOM chrome and CHART_THEMES for the canvas. The two already disagree on secondary values — chart borderColor and axisText differ from --border and --text-dim in five themes, and no test would have noticed a new theme missing tokens entirely.

midnight-slate-pro border #26313d vs chart #223247 · axis #9aa8b8 vs #9fb0c3 amoled-black axis #a7b2bf vs #94a3b8 classic-light border #d1d5db vs #e5e7eb · axis #4b5563 vs #475569 refinitiv-dark axis #a0afbf vs #94a3b8 tos-charcoal axis #a7b1bf vs #abb2bf
Fix: themeSystemAudit.test.ts now asserts token coverage, chart-background parity with --chart-bg, chart text/mark contrast and boot-script id parity. The remaining secondary drift is listed as R-03.
Medium F-06 · getChartTheme returned the shared palette object Fixed

With no custom colours the function returned the module-level CHART_THEMES[id] instance. A single consumer mutating theme.background (or a renderer that normalised a value in place) would silently corrupt that theme for the whole session.

Fix: it now returns a copy; a regression test mutates the result and verifies the source palette is untouched.
Low F-07 · Only Eikon Dark Pro defined a focus-ring token Fixed

button:focus-visible falls back to var(--accent) when --focus-ring is absent, so six themes relied on an implicit fallback. The ring stayed visible, but the contract was accidental and untested except for the fallback.

Fix: every theme now declares --focus-ring; a test asserts ≥ 3:1 against all four panel surfaces.
Medium F-08 · Accent-filled buttons keep a white label at 2.1–3.7:1 Open

Primary buttons use background: var(--accent); color: #ffffff. On AMOLED (#38bdf8) that is 2.14:1, on Charcoal (#61afef) 2.36:1, on Midnight (#3b82f6) 3.68:1 and on Eikon (#0284c7) 4.10:1 — all below 4.5:1 for the 12–13 px labels used.

Recommended: add --accent-contrast per theme (dark ink on light accents, white on dark accents) and use it for filled-button labels. This is a visual change to every primary button, so it was left for explicit approval.
Medium F-09 · Sentinel-value heuristics can discard legitimate user choices Open

Detecting “not customised” by comparing the stored value with the legacy default is pragmatic and backward compatible, but a user who deliberately picks #26a69a, #1e2a3a or #60a5fa is silently ignored.

Recommended: persist an explicit chartColorsCustomized flag (or null for untouched colours) in the application profile, then delete the sentinel table.
Low F-10 · Canvas annotation colours are theme-blind Open

Pattern and scanner markers use fixed hues (#f0c34e neutral, #20d18b bullish, #ff5757 bearish) from ChartCanvas.tsx and Toolbar.tsx. On a white chart background #f0c34e reaches only 1.95:1 and #20d18b 2.31:1, so neutral/bullish markers are hard to see in light themes.

Recommended: resolve marker colours through the chart theme (e.g. theme.candleUp/candleDown plus a themed neutral) instead of literals.
Low F-11 · No “follow system” theme and no per-chart override Open

The theme is a single global application setting. There is no prefers-color-scheme option, and multi-chart layouts cannot mix a light overview with a dark trading chart.

Recommended: add a system pseudo-theme that maps to a light/dark id at runtime (and listens to matchMedia), then consider a per-tab theme override in the tab context menu.
Low F-12 · Residual hard-coded UI colours Open

After the Signal Triggers fix, 14 literal UI colours remain in src/components (mostly deliberate signal/status accents such as #f59e0b for “default template” and #ffb7b7 in the DNN prediction panel error box). Each is a small light-theme legibility risk rather than a structural defect.

Recommended: introduce --warning-text and route these through tokens opportunistically.

What was verified for every theme

  • A CSS block exists for every APP_THEME_IDS entry (default maps to :root).
  • 23 required tokens are present — including the five new text/focus tokens.
  • Chart background equals --chart-bg, so the canvas never sits on a mismatched chrome colour.
  • Candle, wick and crosshair marks stay visible on their own chart background.
  • public/theme-boot.js lists exactly the same theme ids and storage key as the renderer.
The classic-light chart palette is intentionally identical to Classic Light Refined; the refined variant differs only in chrome tokens. That contract is locked by classicLightRefined.test.ts.

Recommendations, in order

  1. R-01 (P1) · Theme the accent label. Add --accent-contrast and apply it to filled buttons — the last widespread AA gap (F-08).
  2. R-02 (P1) · Replace sentinel heuristics with explicit state. Persist a customised flag (or nullable colours) so deliberate choices are never overridden (F-09).
  3. R-03 (P2) · Single source for palette data. Generate the CSS token blocks and CHART_THEMES from one definition file, eliminating the secondary border/axis drift and the need for manual parity tests (F-05).
  4. R-04 (P2) · Theme the canvas annotations. Route pattern/scanner marker colours through the chart theme (F-10) and audit the remaining 14 literal UI colours (F-12).
  5. R-05 (P3) · Follow the operating system. Add a system option with matchMedia('(prefers-color-scheme: dark)'), defaulting new profiles to it (F-11).
Residual risk. Two behaviours are visual rather than logical and are only covered by tests, not by a manual pass: the new text tones in Eikon/Charcoal (lighter red/green) and the theme-aware pre-paint background. A quick visual sweep of Settings → General, Signal Triggers, Bhavcopy status text and the chart legend in each theme is the recommended acceptance step.
